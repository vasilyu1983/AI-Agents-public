## Stance

**Framing (Karpathy, 2025):** context engineering is
*"the delicate art and science of filling the context window with just the right
information for the next step."* The LLM-as-OS mental model is the working
default — the LLM is the CPU, the context window is the RAM, and the application
is the operating system deciding what to load. The runtime verbs and their
attribution are defined once in `references/context-hygiene.md` §Two complementary
verb sets. This discipline is also the **Context & Memory column** of a five-column
**harness** (P19); decisions about what to load only make sense once the harness
budget is fixed.

The durable pattern is not "put everything in a vector DB" — and not "split
everything onto separate vendors" either. Substrate convergence (a document
store with built-in embedding, Postgres + pgvector, or a similar single store) is a
legitimate engineering-economics call when the team is small and one substrate
is already in production. Anti-pattern A8 is about *logical* convergence into
one personalization table; RA9 is about *physical* convergence with strict
logical separation.

The default architecture is:

1. **Operational truth first**: user, org, billing, profile, and product state live behind tools, APIs, or SQL.
   Apply this as: reject any design where a hosted memory or vector store answers "what plan is this customer on?" — that call must go to a tool, API, or SQL query.
2. **Derived memory second**: facts learned over time are stored separately from operational truth and raw conversation logs.
   Apply this as: flag any schema where learned preferences and account state share the same table or collection.
3. **Retrieval for corpora**: domain docs, sites, reports, and broad knowledge sources use evidence-bearing retrieval.
   Apply this as: when the context source is a document corpus, default to RAG with citation metadata rather than baking content into memory rows.
4. **Graph is optional**: use relationship traversal only when the problem actually needs it.
   Apply this as: do not introduce a graph layer unless evals show that relationship traversal changes the answer; default to flat vector retrieval and add graph only on demonstrated multi-hop need.
5. **Context assembly is the product-critical layer**: different surfaces need different bundles, budgets, and trust levels.
   Apply this as: define a named `ContextAssemblyRequest` per surface before writing any retrieval code, and assign explicit token budgets and ACL scopes per surface.
6. **Grounding is mandatory**: context must carry provenance, freshness, ACL scope, and evidence IDs.
   Apply this as: reject any retrieval result that reaches the model without `source_id`, `retrieved_at`, and `owner_scope` fields attached.
7. **Feedback closes the loop**: action outcomes and user corrections should improve the derived layer without corrupting the source of truth.
   Apply this as: route all user corrections through the schema gate (P17) before writing to the memory store, and never write corrections directly to the operational truth system.
8. **Emotional context is a first-class assembly input**: mood, energy, and emotional state should influence how the AI responds (tone), not just what it says (content). Emotional framing of context metadata (warm narrative instead of raw metrics) is the presentation-layer equivalent.
   Apply this as: include an `emotional_context` field in the surface bundle contract and pass it to the response-generation step as a tone modifier, not as factual grounding.
9. **Cross-surface signals flow**: signals captured on one surface (mood from journaling, decisions from dashboard) should be available as context inputs on other surfaces (chat, ask). This requires explicit signal passing or a shared signal store.
   Apply this as: design a shared signal store with explicit publish/subscribe contracts between surfaces rather than letting each surface maintain its own isolated memory.
10. **Context hygiene is as important as storage architecture**: the window itself has runtime failure modes (poisoning, distraction, clash, confusion) that a clean storage design does not prevent. Vocabulary drawn from Drew Breunig's "How Long Contexts Fail" (2025) and Anthropic's "Effective Context Engineering for AI Agents" (2025-09).
    Apply this as: run the F1–F5 failure-mode checklist from `references/context-hygiene.md` on every surface bundle before shipping, independent of storage correctness.
11. **Context rot and mode collapse are the two background failure modes**: rot degrades the substrate (attention quality drops as tokens grow, n² pairwise relationships dilute focus); mode collapse degrades the output distribution (responses converge to a single style, especially when the memory layer re-ingests the model's own outputs as "preferences"). Both compound silently — name them explicitly in evals. See `references/context-hygiene.md`.
    Apply this as: add a KL-divergence mode-collapse eval and a citation-drift rot eval to the CI pipeline, and re-run both after every P14 consolidation cadence change.
12. **Converged datastores are legitimate when guardrails hold**: a single substrate (MongoDB Atlas, Supabase, Convex) carrying operational truth, memory, and chunk retrieval is the right answer for small teams when *logical* separation is preserved (separate collections/tables, separate ACL, separate retention) and the vendor migration path is documented. The risk surface shifts from "too many vendors" to "embedding-model lock-in" (`autoEmbed` and similar) — manage it as a P13 boundary. See RA9 in `references/reference-architectures.md`.
    Apply this as: approve a converged substrate only when a migration-path document exists that estimates re-embedding cost and time for the current corpus before adoption.
13. **Multi-repo KBs are git-anchored, not snapshot-anchored**: when the corpus is a portfolio of git repositories (the `requirements-hub` shape — many repos, many readers, many agents), the canonical store is git itself; the vector index is a derived projection that can always be rebuilt from `git log`. Every chunk row carries `(source_repo, source_path, source_commit_sha, content_hash)` and uses tombstone-on-delete. Diff-based ingestion plus content-hash idempotency keeps freshness lag low without re-embedding the world. See RA10, `references/git-anchored-ingestion.md`, and partner skill `dev-context-multi-repo` for catalog and freshness tooling.
    Apply this as: require `(source_repo, source_path, source_commit_sha, content_hash)` on every chunk row and tombstone-on-delete before approving a multi-repo ingestion design.
14. **Policy / compliance / operational docs need an authority-aware KB**: regulator letters, internal policies, standards, procedures, runbooks, and control-framework mappings (ISO 27001, NIST 800-53, PCI-DSS, PSD2 RTS) must be ingested with `normative_weight`, `effective_from / effective_to`, and a cross-reference graph (`IMPLEMENTS`, `OPERATIONALIZES`, `ENFORCES`, `SUPERSEDED_BY`, `MAPS_TO`). Citations are paragraph-precise (`doc_id, version, clause_id, effective_at`); a regulation always out-ranks a guideline regardless of cosine similarity; reviewer approval before cutover is non-negotiable. Polyglot ingest (git markdown + Confluence + SharePoint + regulator PDFs + Notion) normalizes to one `PolicyChunk` schema. This is RA11 — see `references/policy-and-compliance-docs.md` and the composition map in `references/composition-with-related-skills.md`.
    Apply this as: block any compliance KB launch where regulations and guidelines share the same ranking surface without a `normative_weight` field that ensures regulations always outrank guidelines.
15. **Sleep-time consolidation is a first-class pattern, not a nice-to-have**: practitioner write-ups (Supermemory, Mem0, LinkedIn Cognitive Memory Agent) converge on the view that a `remember`-only loop accumulates rot — duplicate rows, ghost references, "yesterday" baked into stored text. P14 names the *background* job that dedupes, resolves contradictions, rewrites relative→absolute dates, prunes superseded rows, and re-clusters P7 pages. The trap is A31: a poorly-rule-bound consolidator re-ingests the model's own outputs and amplifies mode collapse. Run mode-collapse evals after every cadence change. Some managed agent platforms ship this as a scheduled consolidation feature that writes the consolidated result to a new store and leaves the input unmodified, so the output can be reviewed and eval-gated before adoption; check the platform's current docs for availability, and keep it distinct from a client-side memory directory. See `references/managed-memory-boundaries.md`.
    Apply this as: require a P14 consolidation job with explicit dedup, contradiction-resolution, and date-normalization rules before any memory store that accepts open-ended agent writes ships to production.
16. **Procedural memory is the third tier**: alongside episodic (events) and semantic (facts), a mature stack carries *procedural* memory — reusable skills/playbooks the agent selects rather than reinvents (P15). Recent literature (LEGOMem, SkillFoundry, the techrxiv survey, Anthropic Skills) treats the skill library as memory, with progressive disclosure: only names + descriptions enter the window; bodies load via P12. Filesystem-as-memory (P10) + git review is the dominant substrate.
    Apply this as: model the agent skill/playbook library as a P15 procedural memory store with progressive disclosure — names and descriptions in-context, bodies loaded via P12 on demand.
17. **Multi-agent shared memory needs barriers, not just storage**: P11 isolation prevents coordination; a global blackboard propagates errors. P16 names the boundary discipline — provenance per write, per-agent scratch namespaces, validation gate at promotion, role-keyed namespaces. The new failure (A32 — uncoordinated multi-agent writes) is the load-bearing one to design against. RA12 codifies the recipe.
    Apply this as: require per-agent scratch namespaces and a validation gate at promotion to shared memory before approving any multi-agent architecture; block A32 explicitly in the design review.
18. **Voice has its own latency tier of memory**: synchronous embedding lookup on every turn overshoots the 200–300ms human-conversation budget. RA13 splits memory into a foreground "Fast Talker" hot tier (sub-ms, per-user cache) and a background "Slow Thinker" cold tier (vector recall + pre-fetch + P14 consolidation). The pattern comes from Salesforce's VoiceAgentRAG paper, which reports large cache-hit and retrieval-speed gains on its own benchmark; re-measure on your traffic. A34 names the failure of running chat-tier memory on a voice surface.
    Apply this as: for any voice surface, require a sub-ms hot-tier cache and pre-fetch architecture (RA13) and explicitly block synchronous vector lookup on the turn-by-turn path.
19. **Knowledge-graph utility is now empirically bounded**: GraphRAG-Bench (arXiv 2506.02404, Xiao et al., Jun 2025) makes the tradeoff measurable — graph retrieval earns its keep on multi-hop, cross-document questions and not on single-hop lookups, where a flat baseline is competitive. *Direction only — verify the magnitude before quoting a number: that paper benchmarks GraphRAG variants against BM-25/TF-IDF, not against vanilla semantic RAG, and states no multi-hop point gain. For the graph-vs-vanilla comparison see "When to use Graphs in RAG" (arXiv 2506.05690), which reports that "GraphRAG frequently underperforms vanilla RAG on many real-world tasks".* A33 is the anti-pattern of forcing graph traversal where a flat retrieval would answer in one hop. LazyGraphRAG (~0.1% indexing cost vs full GraphRAG) is the cost-conscious default; reserve full GraphRAG for narrative / multi-hop paths. SOG (Structure of Graph, Feb 2026) compresses topology to a single token for cases where the model needs structural awareness without textual expansion.
    Apply this as: default to LazyGraphRAG; escalate to full GraphRAG only when evals show multi-hop reasoning failures that flat retrieval cannot resolve.
20. **External memory benchmarks exist; use them**: LongMemEval (5 axes, including the load-bearing "knowledge updates" axis), LoCoMo (very-long-term conversational memory), MemBench (factual vs reflective memory, participation vs observation scenarios; effectiveness/efficiency/capacity), GraphRAG-Bench (graph-vs-flat retrieval), MemTier (tiered architecture under long-horizon load). MemoryAgentBench (ICLR 2026, arXiv 2507.05257 — verified) adds a selective-forgetting axis missing from all others; LongMemEval-V2 (May 2026) extends LongMemEval to ~115M-token web-agent histories (work in progress). Pair external benchmarks with the skill's internal eval suites — the external suite measures *capability*, the internal suite measures *architectural discipline*. See `references/agent-memory-benchmarks.md` for SLO starting points.
    Apply this as: select one external benchmark per memory capability and tie a numeric SLO to it in the deployment gate — do not rely on internal evals alone to catch silent regressions.
21. **A provider memory tool is a client-side filesystem-as-memory primitive**: some providers ship a memory tool type that gives agents read/write/list access to a memory directory persisted by the client between sessions. It implements the filesystem-as-memory pattern (P10); it is client-controlled, not a hosted-memory service, so operational truth boundaries (P1, P13) still apply. Look up the provider's current tool type and semantics before wiring it. See `references/filesystem-as-memory.md` and `references/managed-memory-boundaries.md`.
    Apply this as: when a long-running agent needs durable memory and the provider offers a memory tool, back it with your own storage rather than introducing a new memory vendor.
22. **Schema-grounded writes are the primary defense against memory poisoning and mode collapse**: every agent write to derived memory should pass through a schema validation gate before persistence. The gate enforces: (a) required provenance fields (`source_episode_id`, `confidence`, `owner_scope`, `valid_from`); (b) type and range constraints; (c) a contradiction check against existing rows; (d) no raw model output re-ingested as a declared fact without a normalization step. This is the decision node missing from most "remember / recall / reject" implementations — add it between the agent's extraction step and the storage write. Prevents F1 (poisoning) and A26/A31 (mode collapse from self-ingestion). See anti-patterns A13, A26, A31 in `references/anti-patterns-catalog.md`.
    Apply this as: insert a P17 schema validation gate between the agent's memory-extraction step and every storage write, and block any write that lacks `source_episode_id`, `confidence`, `owner_scope`, and `valid_from`.
23. **Tokenizer and minimum-cacheable-prefix values change per model release — re-baseline per model, do not hardcode.** Any token-budget ratio, cap, or per-surface ceiling derived from another model's benchmarks must be re-measured on the model in production, and the minimum cacheable prefix must be read from the live model docs. The 2K–8K per-surface defaults in `references/context-assembly.md` are starting points, not caps. Use an advisory task/effort budget alongside `max_tokens` when budget discipline matters; see `references/context-assembly.md` §Token Budget Management.
    Apply this as: re-measure all per-surface token-budget defaults on the production model before treating the 2K–8K starting points as hard caps, and use the provider's advisory task or effort budget control, where it exists, alongside `max_tokens`.
24. **Context is an evolving playbook, not a fixed prompt (ACE)**: Zhang et al., *Agentic Context Engineering* (arXiv:2510.04618, Oct 2025; Stanford + SambaNova + UC Berkeley) names the **Generator → Reflector → Curator** loop that emits **delta updates** (small additive bullets) to a structured playbook. Reported gains are quoted once, in P18 of `references/patterns-catalog.md`; no fine-tune is involved. The load-bearing mechanic is *delta updates instead of rewrites* — wholesale regeneration causes **A35 context collapse**, where rare-but-important strategies decay geometrically across consolidation cycles. P18 names the pattern; A35 names the failure; pair with P17 (every delta passes the schema gate). Distinct from A26 mode-collapse: A35 is collapse of the stored context distribution; A26 is collapse of the output distribution.
    Apply this as: implement the Curator step with delta updates (additive bullets) rather than full-context rewrites, and run an A35 context-collapse eval after any change to the Curator or P14 Reflector.
25. **The context layer lives inside a harness (Hashimoto, 2026 talk)**: `Agent = Model + Harness`. The harness has five columns — tool orchestration, verification loops, **context & memory** (this skill), guardrails, observability. Naming the parent discipline (P19) makes scope explicit: context-layer choices only make sense once the harness budget is fixed; per-surface token caps are harness decisions, not context-layer ones. **A36 victory-declaration bias** (agents marking work complete without verification evidence) is a harness-level failure that contaminates derived memory if not gated at the P17 schema layer. **A37 eager compaction** is the harness-budget mistake of compacting before there is signal to compress. The canonical `compress` recipe is **P20 Anchored Iterative Summarization** — every summary line carries durable IDs (file path, decision ID, todo ID) so downstream steps can re-resolve.
    Apply this as: fix per-surface token caps at the harness level before designing the context layer, and enforce P20 anchoring (every summary line carries durable IDs) as a gate on the `compact` step.

26. **Mid-conversation system messages let you patch the assembly bundle without paying a full re-prime (verify current model support before relying on this)**: recent Anthropic models accept a `role: "system"` message injected after a user turn, letting a long-running agent append updated instructions, corrected facts, or a refreshed policy snippet later in the conversation instead of restating the whole system prompt. The judgment call this enables: when a P17 schema-gated correction or a P14 consolidation output needs to reach an in-flight agent session, prefer appending a scoped system-message patch over rebuilding and re-sending the full `ContextAssemblyRequest` bundle — it preserves upstream prompt-cache hits and keeps the cost of a mid-session correction proportional to the patch, not the whole bundle. This is a context-assembly-layer optimization, not a memory-write path: the patch still must originate from the P17 gate, and the underlying `EntityProfile`/`LearnedMemory` rows are still the source of truth for the next session's initial assembly.
27. **A synchronized model-family refresh does not mean the numbers transfer across the family**: when a provider ships several models in the same window (for example a run of tokenizer changes, minimum-cache-prefix changes, and new context-editing primitives across a flagship line), treat each model's context-budget, caching, and compaction defaults as independently verified facts, not siblings that inherit the same constants. Two models announced on the same day have shipped different minimum-cacheable-prefix values before; assume this can recur.

## Context Window Failure Modes

Longer context does not mean better answers. Every per-surface bundle must be checked against the F1–F5 runtime failure modes before shipping (F1–F4 = Breunig's taxonomy: poisoning, distraction, clash, confusion; F5 = proactive interference). Full taxonomy with detection signals and recipes in `references/context-hygiene.md`. Context collapse (A35) is tracked separately below because it is a storage-side failure, not an F mode.

| ID | Mode | One-line signal | Primary mitigation |
|----|------|-----------------|--------------------|
| F1 | **Poisoning** | Model cites facts the source of truth does not contain | A13 provenance + A14 confidence + P4 invalidation |
| F2 | **Distraction** | Agent repeats prior actions instead of synthesizing new plans | Token-budget cap + history compaction + P11 sub-agent isolation |
| F3 | **Clash** | Identical inputs produce oscillating behaviors; new tool breaks unrelated tasks | Ingest-time contradiction detection + per-surface tool allowlist |
| F4 | **Confusion** | Model picks the wrong tool; irrelevant memories crowd the bundle | Just-in-time selection + tool allowlist tuned to surface jobs |
| F5 | **Proactive interference** | Recently updated facts are answered with a stale value as prior versions accumulate | Version-tagged slots that supersede prior rows + P14 consolidation tombstones |
| A35 | **Context collapse** (not an F mode) | Playbook/memory converges to terse summaries after N consolidation cycles; edge-case strategies disappear | P18 ACE delta-updates instead of rewrites; A35 sweep; P17 schema gate on every Curator emission |

F1–F4 map to anti-patterns A19–A22; F5 maps to A19 (stale-value variant) and A31; context collapse is A35. They compose with storage-layer anti-patterns — a poisoned memory (F1) is typically the downstream effect of A13 or A14 upstream; A35 is typically the downstream effect of A37 (eager compaction) plus a curator that rewrites instead of patching.

### Runtime verbs (complement to storage verbs)

The storage lifecycle is `remember / recall / forget / improve`. The runtime lifecycle is the six-verb set `write / select / compress / isolate / order / format`; its source and definitions live in `references/context-hygiene.md` §Two complementary verb sets. In brief:

- **write** to persist outside the window (episode log, memory store, scratchpad)
- **select** only what the current step needs, just-in-time
- **compress** summaries and tool-result projections to fit the budget
- **isolate** long-horizon sub-tasks into sub-agents with their own window (P11)
- **order** content deterministically — stable first, volatile last — to keep the KV cache warm and avoid the lost-in-the-middle effect
- **format** tool results, memories, and retrieval hits into typed projections rather than raw payloads, so the model reasons over signal not noise

A26 (mode-collapse loop) blocks correctly only when `format` separates user-stated from model-inferred at write time. **`compress` has a canonical recipe**: P20 Anchored Iterative Summarization — every summary line carries durable IDs (file path, decision ID, todo ID) so the next step can re-resolve any artifact. Where the provider offers server-side compaction or tool-result clearing, look up the current primitive, its default trigger, and whether it accepts custom summarization instructions (use them to enforce anchoring). Tool-result clearing is the orthogonal `select` primitive against tool-result bloat: it drops bulky results while keeping the record that the call happened. Decide when to clear or compact with `references/context-hygiene.md` §Context mutation economics, and verify each compaction with §Compaction verification.

See `references/context-hygiene.md` for the full taxonomy and recipes, and `references/security-threat-model.md` for injection/poisoning threats against the same surface.
