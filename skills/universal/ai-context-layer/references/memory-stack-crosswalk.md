R1–R7 are the stages in [memory-responsibilities-audit](memory-responsibilities-audit.md). Labels: **[V]** verified in a primary source on the fetch date, **[I]** inference, **[U]** vendor claim not independently checked.

## C. Three engine mechanisms

### Letta: background memory subagents

- **Mechanism [V].** Current Letta calls it "dreaming": background subagents review recent conversations, consolidate lessons, and update memory without blocking the main agent. Memory is MemFS, a git repository per agent; files under `system/` load into the prompt every turn; every edit is a commit; memory subagents work in git worktrees.
- **Trigger [V].** `dreaming: { trigger: "step-count" | "compaction-event" | "off", behavior: "reminder" | "auto-launch", stepCount }`. `behavior` is fixed at creation; a session can override `trigger` and `stepCount`. The CLI command is `/sleeptime`.
- **Legacy [V].** The retired V1 API server (repo `archive` branch) had `enable_sleeptime`, a sleep-time group with `sleeptime_agent_frequency`, and block-edit tools `memory_replace`, `memory_insert`, `memory_rethink`, `memory_finish_edits`. Do not start new work on them.
- **Write path.** Subagent edits files → commit → push for cloud-backed agents [V].
- **Keep raw.** Conversation history is stored and searched apart from MemFS [V]; treat it as the episode log [I].
- **Gate promotion.** The commit is the chokepoint: run P17 checks before it lands, require P18-style deltas, and keep a P21 link from each lesson to the conversations behind it [I].
- **Verify first.** A commit gives rollback, not correctness. Plant a contradicted fact, let a dreaming run fire, and confirm the diff supersedes it instead of appending a second version [I].

### LangMem `ReflectionExecutor` → LangGraph `BaseStore`

- **Mechanism [V].** Wraps a memory manager from `create_memory_store_manager` and defers it: `submit(payload, after_seconds=…)`. Per thread, a new submit cancels the pending task and reschedules it (debounce).
- **Local vs remote [V].** Local: an in-process worker thread and priority queue; it needs a store, passed in or taken from the LangGraph runtime. Remote: pass a graph name and URL, and it creates a delayed run on a LangGraph server with the `rollback` multitask strategy. The docs warn local threads end between serverless invocations; use remote there.
- **Write path [V].** The manager searches its namespace (default `("memories", "{langgraph_user_id}")`), a model proposes inserts, updates, and deletes, then it calls `aput` on new or existing keys and `adelete` only when deletes are enabled (off by default in `create_memory_store_manager`).
- **Keep raw.** The store holds extracted memories only; persist the thread or checkpoint as the episode log [I].
- **Gate promotion.** The store manager awaits `aput`/`adelete` before it returns the puts [V], so a check on the returned puts runs after the write. Gate before persistence: extract proposals with `create_memory_manager` (no store), validate the complete mutation batch, then write; or wrap every mutation entry point used (`aput` and `adelete`, plus synchronous equivalents) so both writes and deletions stage [I]. Publish the batch in a transaction with an expected-version check, or atomically switch an approved revision; individual BaseStore calls do not supply that application guarantee [I]. P4 history is yours too: an update replaces the value under the same key.
- **Verify first.** `InMemoryStore` is not persistent [V]; the local queue lives in memory, so pending reflections die with the process [I]. The namespace template is the tenancy boundary; fill it from the authenticated principal, never from model output [I].

### Hindsight async consolidation → PostgreSQL

- **Mechanism [V].** Retain writes facts, entities, and links. A `consolidation` operation then runs after retains and after deletes: a row in the `async_operations` table, claimed by an in-process or dedicated worker, with one pending job per bank. It produces observations (deduplicated beliefs that cite supporting memories with quotes and a proof count). Mental models are standing answers you define; a background refresh rewrites them and keeps prior versions. Storage is Postgres (embedded by default, or external) or Oracle.
- **Write path [V].** `retain` → facts → queued consolidation → observations; `refresh_mental_model` runs as its own operation.
- **Keep raw [V].** The docs say raw facts are always preserved.
- **Gate promotion.** Observations are P21-shaped natively. Turning off auto-consolidation changes scheduling; a manual consolidation still writes observations into the bank used by recall/reflect [V]. Evaluate an isolated candidate bank/revision, or hold a serving gate over candidate observations and dependent mental-model refreshes until approval; continue serving the prior approved revision [I]. Confirm sensitivity and scope carry over from facts to observations [I].
- **Verify first [V].** Reconciliation compares observations within one tag scope only, so a per-session tag yields one near-duplicate per session unless retain sets `observation_scopes: "shared"`. Near-duplicate reconciliation runs on Postgres only. `reflect` treats observations as stale while newer memories are unconsolidated. No native TTL or decay for memory items; the vendor's blog calls eviction a non-goal [U]. Audit-log and LLM-trace rows do have retention sweeps, and traced rows hold full prompts and model outputs [V], so they are in erasure scope. Plant and erase a sentinel fact through observations, mental models, audit logs and traces.

## D. Query modes

Filter rule for every row: tenant, sensitivity, section scope, and validity are part of each leg's query, so only authorized candidates reach fusion, reranking, and context assembly ([P24](patterns-catalog.md#p24--sensitivity-filter-before-retrieval), [P23](patterns-catalog.md#p23--section-level-scope)). That is a logical guarantee, not a physical pre-filter: pgvector HNSW still filters after the index scan, and iterative scans recover recall without changing that [V]; the "Where the filter must run" column holds each engine's recall fix. Fuse with RRF only ranked evidence lists (semantic, lexical); exact lookups, aggregates, and as-of facts stay typed and are returned or cited as they are [I].

| Mode | Question shape | Implementation per stack | Where the filter must run | Failure mode | Depth |
|---|---|---|---|---|---|
| Semantic | Paraphrase, "something like X" | SQLite: sqlite-vec KNN. Postgres: pgvector HNSW. Graph: Neo4j vector index through `SEARCH`. Vector DB: Qdrant, Milvus, Chroma dense | pgvector iterative scans or partitions; Qdrant payload index created before ingest; Milvus `expr` per request; Neo4j filter properties declared in the index [V] | Post-filter recall loss; silent fallback after an embedding change ([A41](anti-patterns-catalog.md#a41--silent-fallback-to-a-weaker-retrieval-path)) | [lexical vs vector vs hybrid](../../ai-vector-brain/references/lexical-vs-vector-vs-hybrid.md), [index defaults](../../ai-vector-brain/references/postgres-pgvector-default.md#index-defaults) |
| Lexical | Identifiers, error codes, clause IDs, names | Exact identifier: equality on an indexed key column, a typed answer that is not fused [I]. Tokenized text: SQLite: FTS5 `bm25()`. Postgres: `tsvector`, or a BM25 extension. Graph: Neo4j full-text index. Vector DB: Qdrant sparse with `idf`, Milvus BM25 function, Chroma Cloud sparse | In each leg's `WHERE`; `pg_textsearch` applies other conditions after scoring [V] | A stemmer that mangles identifiers; index and query tokenizers that differ; `ts_rank` treated as BM25 | [BM25 upgrade](../../ai-vector-brain/references/bm25-when-ts_rank-isnt-enough.md), [ai-rag](../../ai-rag/SKILL.md) |
| Relational | Multi-hop: who or what is connected, ownership chains, "depended on X last quarter" | SQLite or Postgres: recursive CTE over an edges table; Apache AGE inside Postgres [V]. Graph: Cypher traversal. Vector DB: none | On every hop, not only the seed node | Graph for single-hop lookups ([A33](anti-patterns-catalog.md#a33--graphrag-misapplied-to-single-hop-lookups)); edges without evidence ([A42](anti-patterns-catalog.md#a42--relation-edges-asserted-without-text-evidence)) | [graph layer](graph-and-relationship-layer.md) |
| Structured | Counts, latest, sums, "true at t" | SQL templates over typed tables with the 012 as-of predicate; text-to-SQL only as fallback, under a read-only role, timeout, and allowlisted views. Graph: Cypher aggregates. Vector DB: bounded filtered operations only, such as Qdrant's count with `exact: true` [V]; joins, as-of facts, and cross-table aggregates route to SQL [I] | Row-level security or scoped views | Silent partial aggregate ([A45](anti-patterns-catalog.md#a45--silent-partial-aggregate)); vector top-k undercounting | [Retrieval stage](memory-responsibilities-audit.md#5-retrieval), [P25](patterns-catalog.md#p25--schema-first-typed-memory), [mcp-for-dwh](../../agents-mcp/references/mcp-for-dwh.md) |

## E. Default stacks by scale

Consistent with the [scenario playbooks](memory-scenario-playbooks.md); each upgrade waits for its trigger. These are workload defaults, not a vendor ranking: compare held-out answer quality, filtered recall, p95 latency, deletion correctness, and operating cost against the simpler stack before adopting another service [I].

- **Single developer or local.** Start from the scenario's smallest default (for coding memory, files plus git plus a progress log). Add a JSONL episode log, then one SQLite file with FTS5 and sqlite-vec, when the playbook's index trigger fires. From Bun, use `bun:sqlite`; on macOS, `setCustomSQLite` first. **Upgrade trigger:** measured write contention (SQLite serializes writers across processes; try WAL and `busy_timeout` first [I]), a second device, an availability requirement, or a store too large for brute-force KNN under the eval → Postgres. Playbooks [3](memory-scenario-playbooks.md#3-coding-agent-memory) and [11](memory-scenario-playbooks.md#11-on-device--privacy-first).
- **Team or product.** Postgres with pgvector, RLS, and 012 bitemporal facts; add a BM25 extension when `ts_rank` misses the lexical slice; run consolidation as a `pg_cron` or queue job. **Upgrade trigger:** relationship-history questions, or vector volume and filtered recall that pgvector cannot hold under the eval. Playbooks [1](memory-scenario-playbooks.md#1-personal-assistant--end-user-memory), [2](memory-scenario-playbooks.md#2-customer-support--crm-multi-tenant), [7](memory-scenario-playbooks.md#7-incident--ops-memory-with-point-in-time-ownership).
- **Relationship-heavy.** Add Neo4j or FalkorDB (through Graphiti) only when traversal changes answers (the A9 test). Postgres stays the system of record and feeds the graph through an outbox. **Upgrade trigger:** multi-hop or "who, when" history questions that recursive CTEs answer wrongly or too slowly. Playbook [6](memory-scenario-playbooks.md#6-multi-repo-code-hub).
- **Large vector corpora.** Qdrant or Milvus behind an outbox from the system of record; facts, erasure, and as-of answers stay in Postgres. **Upgrade trigger:** the escalation triggers in [backend-selection](../../ai-vector-brain/references/backend-selection.md#escalation-triggers).

**Background consolidation default [I].** Persist scoped jobs with episode writes through a transactional outbox; workers use leases, retries, and idempotency keys. Read a bounded source revision, stage inserts and deletions with lineage, and recheck authority, expiry, tombstones, and source versions before publishing. Promote an approved revision atomically; stale jobs must not resurrect erased evidence. Keep the previous approved revision available while evaluating candidates. Letta, LangMem, and Hindsight supply different parts of this pattern; none is assumed to provide the whole application contract.

## F. Vocabulary

Bitemporal terms follow [P4](patterns-catalog.md#p4--temporal-knowledge-graph-with-bi-temporal-facts): `valid_from` / `valid_to` for valid time, `recorded_at` / `superseded_at` for transaction time. Map engine-native names there (Graphiti uses `valid_at`, `invalid_at`, `created_at`, `expired_at`).
