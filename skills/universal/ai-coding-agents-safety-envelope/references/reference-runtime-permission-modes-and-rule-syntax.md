# Permission Modes, Rule Syntax, and Settings Precedence

Moved from the former permissions skill. The main SKILL.md carries the durable rules; this file carries the reference-runtime detail an expert checks during a permission audit.

## Reference Runtime: Permission Modes

Look up the target runtime's current mode list, starting mode, and classifier eligibility in its permission-modes doc before writing tooling or config against them. Mode names, the starting mode, and what each mode auto-approves change between releases. The durable rules:

- **Mode ladder.** Place every vendor mode on one ladder of what runs without a prompt: read-only → workspace edits → classifier-approved actions → allowlist-only (headless) → bypass. Copy the rung, not the name.
- **Protected paths run before allow rules.** Repository metadata (`.git`), editor and tool config directories, the agent's own config directory, and shell and package-manager rc files get a hard-coded carve-out that no allow rule reaches in any mode below bypass. In one shipping runtime, an `Edit(.claude/**)` allow rule does not unlock `.claude`.
- **Entering a classifier mode drops broad allows.** Blanket shell, interpreter, and package-manager-run allow rules are suspended on entry and restored on exit; narrow rules carry over. The classifier is a server-side model independent of the session's model, so do not pin its name. Tool results are stripped from its input and scanned separately for injected instructions. Decision order: explicit rules first (protected paths excepted), then read-only and in-workspace edits, then the classifier.
- **Denial circuit breaker with an explicit headless fallback.** After repeated classifier denials the runtime falls back to prompting; look up the threshold. With no user to prompt, state the headless fallback: in one shipping runtime the denied action does not run and the run keeps working rather than aborting. Never leave it to a hang or an assumption.
- **A repo cannot grant itself a classifier or bypass mode.** Project-scoped settings that request one are ignored; only user or managed scope may set it, and the managed layer can remove the classifier mode entirely.
- **Allowlist-only headless mode is the CI mode.** Anything that would prompt is denied; only allow-rule matches and read-only commands run. A tool whose consent card needs an interactive answer is denied even when an allow rule matches it.
- **Subagents cannot escalate past the parent.** A parent in a classifier mode overrides a subagent's own mode setting and checks delegated work at spawn, at each action, and on completion. Plugin-shipped agents cannot set their mode, hooks, or MCP servers.
- **Auto-deny only when no controller exists.** A background subagent that needs approval should surface the request in the parent session, labeled with the subagent's name, so the parent can approve or deny that one call without stopping it. Default to silent denial only when no parent or leader session is reachable; route the pending approval there as a first-class object (see [Permission Runtime Model](permission-runtime-model.md)).

### Rule syntax an expert checks first

- **Evaluation order is fixed, not precedence-weighted**: deny, then ask, then allow — first match wins regardless of specificity. A broad `Bash(aws *)` deny still blocks a narrower `Bash(aws s3 ls)` allow; there is no allowlist-exception mechanism inside a deny rule.
- **Parameter-matching rules** (`Tool(param:value)`) let deny/ask rules gate on any top-level scalar input field, e.g. `Agent(model:opus)` or `Agent(isolation:worktree)` or `Bash(run_in_background:true)`. This is distinct from — and composes with — the older `Agent(AgentName)` subagent-identity rule. Fields a tool already canonicalizes (`command` for Bash, `file_path` for Read/Edit/Write) are excluded from this path and must use the tool's own specifier syntax; a `Bash(command:rm *)` rule is silently ignored with a startup warning because it would be bypassable by a compound command.
- **Path-anchor bugs are the most common review finding**: `//path` is filesystem-absolute; `/path` is relative to *the settings file that defines the rule*, not the project root or the CLI's cwd. A `Read(/secrets/**)` deny written into `~/.claude/settings.json` blocks `~/.claude/secrets/**`, not a project's `secrets/` directory — reviewers should flag every single-leading-slash path rule in user settings as a likely mistake.
- **Symlinks split allow/deny asymmetrically**: allow rules require both the symlink path *and* its resolved target to match (otherwise it falls back to prompting); deny rules fire if *either* the symlink path or the target matches. A symlink into an allowed directory pointing outside it is not auto-approved by that fact alone.
- **Hooks are best-effort, not enforcement**: a `PreToolUse` hook's `if` field scopes it with permission-rule syntax (e.g. `if: "Bash(rm *)"`), but the filter fails open — if the Bash command can't be parsed, the hook runs anyway. Deny/ask permission rules are evaluated independently of what a hook returns, so a hook cannot be the sole enforcement point for a hard boundary; it can add checks, not replace deny/ask rules. See [`../agents-hooks/SKILL.md`](../../agents-hooks/SKILL.md) for hook event and matcher design.

### Settings precedence, briefly (permission-audit nuance only)

Full precedence chain — **managed settings > CLI arguments > local project (`.claude/settings.local.json`) > shared project (`.claude/settings.json`) > user (`~/.claude/settings.json`)** — is [`../ai-coding-agents-settings-policy/SKILL.md`](../../ai-coding-agents-settings-policy/SKILL.md)'s territory; use it for full source layering and managed-policy design.

The one nuance load-bearing for a *permission* audit: that precedence order governs plain settings (e.g. `spinnerTipsEnabled`), but permission rules do not simply follow "higher scope wins." **A deny rule from any scope blocks the action regardless of scope precedence** — a user-level deny blocks a project-level allow and a project-level deny blocks a user-level allow, because deny is evaluated before allow at every scope and rules merge across scopes rather than one file overriding another wholesale. Do not assume "project settings win over user settings" applies to allow-vs-deny conflicts — check which rule is a deny before applying the file-precedence mental model.
