# commit_validator.py

Stdlib-only Python CLI for validating and linting Conventional Commit messages. No external dependencies — runs with any Python 3.9+ installation.

## Purpose

Gives developers and CI pipelines fast, reproducible answers to three core questions:

1. **Validate** — Does a single commit message pass Conventional Commits rules? What is wrong, and what should it be instead?
2. **Lint** — How healthy is a commit history? Per-message PASS/WARN/FAIL with a summary of the most common violations.
3. **Report** — A full Markdown quality report with executive summary, violation breakdown, per-commit table, and an attention list for non-passing commits.

## Quick Start

Run from the `dev-git-commit-message/` directory:

```bash
# Validate a single message — PASS
python scripts/commit_validator.py validate --message "feat(auth): add refresh token rotation"

# Validate a single message — FAIL (no type prefix)
python scripts/commit_validator.py validate --message "update"

# Validate a single message — FAIL (banned word)
python scripts/commit_validator.py validate --message "fix stuff"

# Validate a single message — WARN (non-imperative tense)
python scripts/commit_validator.py validate --message "feat(ui): added dark mode toggle"

# Lint a batch of commit messages from a JSON history file
python scripts/commit_validator.py lint --input data/sample-commit-history.json

# Lint without ANSI colour (useful for CI logs)
python scripts/commit_validator.py lint --input data/sample-commit-history.json --no-color

# Full Markdown report printed to stdout
python scripts/commit_validator.py report --input data/sample-commit-history.json

# Full Markdown report written to a file
python scripts/commit_validator.py report --input data/sample-commit-history.json --output /tmp/commit-report.md
```

## Input Format

The `lint` and `report` subcommands read a JSON array where each element is a commit object:

```json
[
  {
    "hash":    "a1b2c3d",
    "message": "feat(auth): add refresh token rotation",
    "author":  "elena.kovacs",
    "date":    "2026-03-18"
  }
]
```

| Field | Required | Notes |
|-------|----------|-------|
| `message` | yes | The commit subject line being validated |
| `hash` | no | Short 7-character hash; shown in lint/report output |
| `author` | no | Author username or display name |
| `date` | no | ISO date string (YYYY-MM-DD); shown in report detail |

See `data/sample-commit-history.json` for a 20-commit example with a realistic mix of passing, warning, and failing messages.

```
python scripts/commit_validator.py validate --help

```

## Validation Rules

| Rule | Threshold | Status |
|------|-----------|--------|
| Type prefix required | `<type>: <summary>` or `<type>(<scope>): <summary>` | FAIL |
| Valid type | feat, fix, perf, refactor, docs, test, build, ci, chore, style, revert | FAIL |
| Type must be lowercase | — | FAIL |
| Scope must be lowercase | — | FAIL |
| No trailing period on summary | — | FAIL |
| Banned summary phrases | update, wip, misc, update stuff, fix stuff, change code | FAIL |
| No tool/AI attribution | generated by, claude, copilot, chatgpt, ai assistant | FAIL |
| Subject line hard limit | ≤72 chars | FAIL |
| Imperative mood | no past/present-continuous first word (added, fixing, …) | WARN |
| Subject line soft limit | ≤50 chars preferred | WARN |

## Exit Codes

| Code | Meaning |
|------|---------|
| `0` | All messages PASS or WARN |
| `1` | One or more messages FAIL (or any error in argument parsing) |
