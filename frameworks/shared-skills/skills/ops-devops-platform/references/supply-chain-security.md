# Supply-Chain Security

*Purpose: Baseline controls for software supply-chain integrity — provenance, attestation, signing, and SBOM. Frame as 2026 procurement table-stakes for any externally-shipped or regulated workload.*

*Use when:* Designing a CI/CD pipeline that needs artifact provenance, responding to a procurement security questionnaire, or evaluating supply-chain gaps in an existing platform.

## SLSA Build Track

Supply-chain Levels for Software Artifacts (SLSA) defines a graduated set of build-integrity guarantees. The current specification is **SLSA v1.2** — SLSA v1.0 is retired. Source: https://slsa.dev/spec/v1.2

### Build levels

| Level | Requirement | Typical gate |
|-------|-------------|--------------|
| L1 | Provenance exists — build produces a signed provenance document | CI generates and uploads provenance; acceptable for internal tooling |
| L2 | Hosted build — build runs on a hosted, two-party build platform; provenance is generated by the platform, not the build script | GitHub Actions / GitLab CI with SLSA provenance generator action |
| L3 | Hardened build — build platform is hardened against tampering; the source reference is immutable; build is hermetic or near-hermetic | Hermetic builds, isolated runners, provenance signed by the build platform key |

### Procurement posture (2026)

- **L1** is the minimum bar most vendor security questionnaires now require for container images.
- **L2** is sufficient for most SaaS and internal platform workloads.
- **L3** is expected for regulated industries (financial services, healthcare) and government supply chains.

Reaching L2 in GitHub Actions requires the official `slsa-framework/slsa-github-generator` action. Reaching L3 requires hermetic build tooling (Bazel, Gradle Enterprise with network isolation, or a dedicated hermetic CI platform).

### Quick rule

Default to L2 for all container images shipped externally; target L3 when regulatory or contractual requirements demand it. Do not cite or link SLSA v1.0 — it is the retired page.

## Sigstore — Keyless Signing

Sigstore is the open-source project providing the infrastructure for keyless artifact signing. Its three components work together:

- **cosign** — CLI and Go library for signing and verifying container images, OCI artifacts, and blobs. Signs using OIDC identity tokens (no long-lived keys to rotate or leak).
- **Fulcio** — Certificate authority that issues short-lived code-signing certificates tied to OIDC identities (GitHub Actions workload identity, Google/GitHub/Microsoft accounts).
- **Rekor** — Immutable, append-only transparency log. Every signature event is recorded; signers cannot deny a signing event and verifiers can audit the full chain.

### Signing flow (keyless)

```
Build completes in CI
  -> cosign requests certificate from Fulcio (presenting OIDC token)
  <- Fulcio issues short-lived cert (valid ~10 minutes)
  -> cosign signs artifact, pushes signature + certificate to OCI registry
  -> cosign records the signing event in Rekor
Verifier:
  -> cosign verify --certificate-identity <identity> --certificate-oidc-issuer <issuer>
  -> Rekor inclusion proof confirms the event was logged at signing time
```

### Enforcement

Add `cosign verify` as a required step in admission (policy-as-code rule) or in the CD pipeline before promotion to production. Any image that cannot be verified against the expected OIDC identity and issuer must be blocked.

### Quick rule

Use cosign keyless signing with GitHub Actions OIDC by default. Rotate to hardware-backed keys only when the signer is a human, not a CI identity.

## in-toto Attestations

in-toto is a framework for expressing and verifying supply-chain attestations. An attestation is a signed statement from a trusted authority about an artifact or a step in the build process.

Common attestation predicates:

- **SLSA Provenance** — records the build inputs, builder identity, and build parameters.
- **SPDX / CycloneDX SBOM** — lists the components of a software artifact.
- **Vulnerability scan results** — records the scan tool, version, and findings at build time.
- **Code review** — records that a human or automated review approved the source change.

Attestations are attached to artifacts as OCI manifest annotations or as files in a well-known location. Verification chains from the artifact back through every attested step.

### Quick rule

Write at least SLSA Provenance and SBOM attestations for every externally-shipped image. Use the `slsa-framework/slsa-github-generator` action in GitHub Actions to generate SLSA provenance automatically.

## SBOM

A Software Bill of Materials (SBOM) is a structured inventory of components, licenses, and dependency relationships in an artifact.

Two dominant formats:

| Format | Governing body | Use |
|--------|---------------|-----|
| **SPDX** | Linux Foundation / ISO 5962 | Preferred for open-source and government supply chains; richer license expression |
| **CycloneDX** | OWASP | Preferred for security use cases; native VEX (Vulnerability Exploitability eXchange) support |

Generate SBOMs at build time, attach as OCI attestations, and store alongside the image digest. Do not generate SBOMs on demand at scan time — a build-time SBOM reflects actual inputs; a post-hoc SBOM is reconstructed and may miss transitive dependencies.

### Quick rule

Generate SBOMs in both SPDX and CycloneDX formats if the downstream consumer is unknown. If the consumer is known, match their preferred format.

## Toolchain (Syft / GUAC)

### Syft

Syft (Anchore) generates SBOMs from container images, filesystems, and source repositories. Supports both SPDX and CycloneDX output. Integrates natively with `cosign` to attach the SBOM as an OCI attestation.

```bash
# Generate and attest SBOM in CI
syft packages <image> -o cyclonedx-json > sbom.cyclonedx.json
cosign attest --type cyclonedx --predicate sbom.cyclonedx.json <image>
```

### GUAC (Graph for Understanding Artifact Composition)

GUAC (OpenSSF project) ingests SBOMs, SLSA provenance documents, and vulnerability data, then builds a queryable graph of the full dependency tree across all artifacts in an organization. Useful when:

- You need to answer "which of our services depends on Log4j?" across dozens of repos.
- You need to trace provenance from a running container image back through every build step and source commit.
- You need to generate compliance evidence for a specific artifact at audit time.

GUAC is not a replacement for Syft — Syft produces the SBOM; GUAC consumes and correlates it at scale.

## CI Integration Pattern

Minimum supply-chain baseline for a GitHub Actions pipeline shipping a container image:

```yaml
jobs:
  build-and-attest:
    permissions:
      id-token: write      # required for OIDC / cosign keyless
      contents: read
      packages: write
      attestations: write  # required for GitHub native attestation API
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t $IMAGE .
      - name: Push image
        run: docker push $IMAGE
      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          image: ${{ env.IMAGE }}
          format: cyclonedx-json
      - name: Generate SLSA provenance
        uses: slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@v2
        # produces L3 provenance; L2 is available via the non-container workflow
      - name: Sign image (keyless)
        run: cosign sign --yes $IMAGE
```

Adapt to GitLab CI by replacing OIDC token issuance with GitLab's built-in OIDC support and replacing the GitHub-specific action references with equivalent CLI calls.

### Enforcement gate (admission)

Add a Kyverno or OPA/Gatekeeper policy that:
1. Checks that every container image in a Pod spec has a valid cosign signature from the expected OIDC issuer.
2. Checks that a CycloneDX or SPDX SBOM attestation exists for the image digest.
3. Blocks admission if either check fails.

## Anti-Patterns

- Signing images with a long-lived private key stored as a CI secret — key rotation and revocation are operational liabilities; use keyless signing.
- Generating SBOMs only on demand at scan time — reconstructed SBOMs miss transitive dependencies that were present at build time.
- Attaching provenance to the image tag rather than the image digest — tags are mutable; always reference and verify by digest.
- Treating SLSA L1 as the finish line for regulated workloads — L1 only guarantees provenance exists; it provides no guarantee about build-platform integrity.
- Citing or linking SLSA v1.0 — that page is retired; the current spec is v1.2 at https://slsa.dev/spec/v1.2
