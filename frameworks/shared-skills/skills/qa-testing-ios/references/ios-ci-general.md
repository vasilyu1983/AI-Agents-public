## Principles

- Keep PR coverage thin: smoke and critical-path tests only.
- Keep full regression scheduled or branch-gated, not on every PR.
- Always persist `xcresult` bundles.
- Re-check environment facts before pinning runner labels, Xcode versions, or simulator runtimes.
- Split build and test when reruns are common: `build-for-testing` then `test-without-building`.

## Baseline Flow

```bash
# Resolve packages once
xcodebuild -resolvePackageDependencies \
  -workspace MyApp.xcworkspace \
  -scheme MyApp

# Compile test products once
xcodebuild build-for-testing \
  -workspace MyApp.xcworkspace \
  -scheme MyApp \
  -destination 'platform=iOS Simulator,name=<simulator-name>,OS=latest' \
  -derivedDataPath ./DerivedData

# Run tests from prebuilt artifacts
xcodebuild test-without-building \
  -workspace MyApp.xcworkspace \
  -scheme MyApp \
  -destination 'platform=iOS Simulator,name=<simulator-name>,OS=latest' \
  -derivedDataPath ./DerivedData \
  -resultBundlePath TestResults.xcresult
```

## Environment Checks

Before the first test command in CI, verify:

- the scheme exists and is shared
- the test plan exists if one is referenced
- the destination exists in that environment
- the simulator runtime you expect is actually installed

Useful commands:

```bash
xcodebuild -list -workspace MyApp.xcworkspace
xcodebuild -scheme MyApp -showTestPlans
xcodebuild -scheme MyApp -showdestinations
xcrun simctl list devices available
xcrun xctrace list devices
```

## Artifacts

Keep these by default:

- `TestResults.xcresult`
- raw `xcodebuild` log
- screenshots or attachments generated by the test framework

Turn on extra diagnostics only when justified:

```bash
-collect-test-diagnostics on-failure
```

## Parallelization

Use parallelization only when tests are:

- order-independent
- state-isolated
- safe to run on multiple simulators at once

Typical pattern:

```bash
xcodebuild test \
  -scheme MyApp \
  -destination 'platform=iOS Simulator,name=<simulator-name>,OS=latest' \
  -parallel-testing-enabled YES \
  -maximum-parallel-testing-workers 4 \
  -resultBundlePath TestResults.xcresult
```

## Repetition And Retry

Use retries as a signal, not a green-build strategy.

```bash
# Prove a flake locally or in a quarantine lane
xcodebuild test \
  -scheme MyApp \
  -destination 'platform=iOS Simulator,name=<simulator-name>,OS=latest' \
  -only-testing:MyAppUITests/LoginFlowTests/testHappyPath \
  -run-tests-until-failure \
  -test-iterations 25

# Short CI retry for diagnosis
xcodebuild test \
  -scheme MyApp \
  -destination 'platform=iOS Simulator,name=<simulator-name>,OS=latest' \
  -retry-tests-on-failure \
  -test-iterations 2 \
  -test-repetition-relaunch-enabled YES \
  -resultBundlePath TestResults.xcresult
```

## Locale, Region, And Permissions

Make environment-sensitive behavior explicit.

```bash
xcodebuild test \
  -scheme MyApp \
  -destination 'platform=iOS Simulator,name=<simulator-name>,OS=latest' \
  -testLanguage en \
  -testRegion GB \
  -resultBundlePath TestResults.xcresult
```

Simulator permissions can be pre-set with `simctl privacy` when the platform supports it.

## CI Platform Choice: Cost And Fit

Three viable platforms for iOS CI, each with a different cost shape and operational tradeoff. Pick by workload volume and control needs, not by default habit — re-verify all rates before committing budget, since Apple and GitHub have both repriced before.

| Platform | Compute cost shape (verify before committing) | Best fit | Watch out for |
|---|---|---|---|
| GitHub Actions (hosted macOS) | ~$0.062/min overage, 10x multiplier against included minutes (Jan 2026 repricing — see `ios-ci-github-actions.md → Cost Notes`) | Low-to-medium volume, teams already on GitHub, want zero infra ownership | Bill scales fast once nightly/full-matrix runs are frequent; runner-image drift |
| Xcode Cloud | 25 compute-hours/month included with Apple Developer Program; paid tiers from $49.99/100 hrs up to $3,999.99/10,000 hrs (~$0.008/min at the 100-hr tier) — verify at [developer.apple.com/xcode-cloud](https://developer.apple.com/xcode-cloud/) before budgeting | Teams wanting first-party App Store Connect integration, TestFlight handoff, minimal YAML | Workflow config lives in Xcode/App Store Connect UI, not versioned alongside other CI as easily; less flexible for non-Apple-ecosystem steps |
| Self-hosted macOS (Mac minis, cloud Mac providers) | Fixed monthly hardware/rental cost regardless of usage | High, steady volume where per-minute billing would exceed fixed cost; need pinned simulator/Xcode matrix | Own the patching, runtime installs, and queue capacity; drift risk moves from "GitHub changed the image" to "nobody updated the box" |

Decision heuristic: start hosted (GitHub Actions or Xcode Cloud, whichever matches your existing tooling) while volume is low. Recompute the crossover to self-hosted once nightly + PR-gate + release-candidate runs push monthly compute hours high enough that fixed hardware cost undercuts metered billing — this crossover point moves whenever either provider reprices, so treat it as a periodic re-check, not a one-time decision.

## CI Review Checklist

- The workflow never assumes `macos-latest` means the same environment next month.
- Runner image, Xcode, and simulator runtime are either explicitly pinned or explicitly verified at runtime.
- `xcresult` is always uploaded.
- The suite can reproduce one failing test in isolation.
- Rerun-pass tests are treated as flakes and tracked.

## Sources To Check Before Pinning

- Apple Xcode release notes
- Apple Xcode Cloud release notes if using Xcode Cloud
- CI provider image documentation for installed Xcode versions and runtimes

## Release-CI on top of test-CI

Test-CI (everything above) verifies the suite is green. Release-CI verifies the app actually ships. They are different gates and must both be wired before a branch is considered releasable.

### Build action ≠ Archive action

`xcodebuild build` validates compile and link. `xcodebuild archive` also runs code-signing, packages into an `.ipa`, and is the path the App Store accepts. **Green Build + red Archive is a normal failure mode.** A release gate that only runs `build-for-testing` passes even when signing, provisioning, or device-family bake is broken. Always run `archive` against a release configuration on the release branch before tagging, not just on release day.

### Xcode Cloud `ci_scripts/ci_post_clone.sh` contract

When targeting Xcode Cloud (or any fresh-clone CI that does not run your local generators), wire the post-clone hook:

- **Path:** exactly `ci_scripts/ci_post_clone.sh` at the repo root. Xcode Cloud runs nothing else by convention.
- **Permissions:** executable (`chmod +x`). Commit the executable bit.
- **Exit code:** must return 0. A non-zero exit aborts the build with no useful summary.
- **Log location:** under the **Post-Clone** step in the Xcode Cloud build log. If the step is missing entirely, the hook did not run — check the path and executable bit first.
- **Typical responsibilities:** synthesise a shim `.env` from Xcode Cloud environment variables, call `scripts/generate-infoplist.sh` / any manifest generator, verify required files exist. Do not run `xcodegen` on CI — the committed `.xcodeproj` is authoritative; regenerating it reshuffles file UUIDs and invalidates DerivedData caches.

### `xcodebuild` exit code 65 diagnostic loop

The summary view always says `Command … failed with a nonzero exit code` or `exit code 65`. The real error is in the nested step output. Before treating the build as unexplainable:

1. Expand the failing step in the Xcode Cloud log UI (or `tail -200` the raw `xcodebuild` log on other CIs).
2. Grep the inner output for: `error:`, `warning:`, `No profiles for`, `requires a development team`, `couldn't be opened`, `PhaseScriptExecution`.
3. Match against the 5 common root causes: missing provisioning profile, missing entitlement capability on the App ID, missing generated file, no Team on the workflow, wrong build-vs-archive action. See `software-mobile/references/app-store-connect-checklist.md → Phase 6 → xcodebuild exit code 65`.

Never treat exit 65 as a transient flake and retry without triaging the nested output. It is signal, not noise.

### Xcode Cloud environment-variable plumbing

Xcode Cloud does not share env files with local machines. Release-CI configuration lives in **App Store Connect → Xcode Cloud → product → Settings → Environment Variables**:

- Mark API keys and tokens as **Secret**. Non-secret vars are visible in logs.
- Set both `Build` and `Archive` workflows — they don't share variable scope by default.
- Every variable used by `ci_post_clone.sh` must have a fallback in the script for when it's unset, otherwise a forgotten secret takes the build down with a generic exit-65. Prefer "generator falls back to a safe default" over "script exits with an error" for non-critical vars.
- Audit by running the script locally with the vars intentionally unset, not just when they're set.
