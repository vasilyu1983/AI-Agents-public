# Primitive: Transition Tree (TT)

**Source**: Goldratt (1994), *It's Not Luck*; Dettmer 2007, *The Logical Thinking Process* (Transition Tree chapter — verify chapter number against your printing before citing it precisely; note some later Dettmer material de-emphasizes the Transition Tree in favor of a more detailed Prerequisite Tree paired with critical chain scheduling).

## Definition

The Transition Tree (TT) is the most granular TOC Thinking Process tool. It translates Intermediate Objectives (from the Prerequisite Tree, primitive 07) into specific, sequenced actions with explicit "need" statements that connect each action to the next state.

**Logic**: Necessity logic at the action level. Each step follows this pattern:
"*Because [current reality / need exists], and [action taken], therefore [new reality / effect].*"

The TT is the bridge between strategy (FRT + PRT) and execution (task list). It adds "why this action, right now" to every step.

## When to Use

- After a Prerequisite Tree has identified IOs: use the TT to detail the action plan for each IO.
- When a team has agreed on a direction but needs explicit "do this, then this" sequencing.
- For high-stakes or novel implementation steps where step-by-step clarity reduces error.
- Change management: TT makes the logic of each action visible, reducing resistance.

## Inputs

- A single Intermediate Objective from the PRT.
- Current reality state (where things stand today for this IO).
- Specific actions that will advance the state toward the IO.

## Outputs

- A step-by-step action sequence with explicit "need" and "effect" for each step.
- A verification check: each step's "effect" must be directly observable.
- A clear "done" state that matches the IO from the PRT.

## Failure Modes

| Failure | Root Cause | Fix |
|---------|-----------|-----|
| TT used for the entire project | TT is too granular for multi-IO scopes | Use PRT for the project; TT only for individual IOs |
| Actions stated without "need" | Steps disconnected from reality; logic invisible | Write the "need" before every action |
| "Effect" stated as an opinion | "People will be happier" is not observable | State effects as observable, checkable outcomes |
| TT replaces conversation | Written TT assumes shared context; team has not read it | Walk through the TT verbally on first use |
| Actions too large | "Implement the system" is not an action | Actions should be completable in ≤ 1 day |

## Worked Example

**IO from PRT**: Define and ratify T/CU-based prioritization criteria.

| Need | Action | Effect |
|------|--------|--------|
| No criteria exist; decisions are ad hoc | Facilitator drafts a one-page criteria proposal using T/CU framework | A specific proposal exists for review |
| Proposal needs stakeholder input | Share draft with Engineering and Product leads for 48-hour async review | Comments and objections documented |
| Objections unresolved block adoption | Schedule a 60-minute working session to address objections | Agreed criteria text exists |
| Agreement not durable without sign-off | Circulate criteria doc for formal sign-off from VP Eng and VP Product | Signed document on record |
| Criteria not known to team | Publish to team wiki and present at next all-hands | Team can cite the criteria |

**Done state**: Criteria published, signed, known by team. PRT IO achieved; move to next IO.
