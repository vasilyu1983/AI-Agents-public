# Practice Scan Targets (Mode B)

What to look for when scanning real production repos for dev practices. Output of a Mode B scan typically feeds `dev-git-workflow`, `qa-*`, and `ops-*` skills.

## What to Fetch

| Asset | Path | Why it matters |
|-------|------|----------------|
| CI workflows | `.github/workflows/*.yml` | Required checks, test matrices, release jobs, caching strategy |
| Required-check config | `.github/branch-protection.yml` or `settings.yml` | Branch protection rules (often enforced via Probot Settings app) |
| CODEOWNERS | `CODEOWNERS` or `.github/CODEOWNERS` | Review routing, ownership boundaries |
| PR template | `.github/PULL_REQUEST_TEMPLATE.md` | What the team demands before review (risk, test plan, rollback) |
| Issue templates | `.github/ISSUE_TEMPLATE/` | Triage discipline |
| Contributing guide | `CONTRIBUTING.md` | Local dev setup, commit conventions, PR expectations |
| Security policy | `SECURITY.md` | Vulnerability handling, CVE channels |
| ADRs | `docs/adr/` or `docs/architecture-decisions/` | Architecture rationale (gold if present) |
| Release config | `release-please-config.json`, `.changeset/`, `.goreleaser.yml` | Release cadence + automation |
| Renovate/Dependabot | `renovate.json`, `.github/dependabot.yml` | Dep-update discipline |

## High-Value Patterns to Mine

| Pattern | Signals to look for | Where it feeds |
|---------|---------------------|----------------|
| **Merge queue config** | `.github/workflows/` using `merge_group` trigger; branch protection requires `merge_queue` | `dev-git-workflow` |
| **Required checks** | Protected branch rules + specific check names | `dev-git-workflow`, `qa-*` |
| **Review SLA signals** | auto-assign config; probot-scheduled reminders; CODEOWNERS with multiple assignees | `dev-git-workflow` |
| **Stacked/graphite workflow** | Graphite config; references to `gt`; small/chained PRs in history | `dev-git-workflow` |
| **Conventional Commits enforcement** | commitlint config; release-please; changeset-bot | `dev-git-commit-message` |
| **CI caching strategy** | actions/cache keys, turbo/nx remote caching | `ops-devops-platform` |
| **Release cadence** | release-please PRs, changeset PRs, manual release workflow | `dev-git-workflow`, `ops-*` |
| **Test matrix layout** | strategy.matrix in workflows; OS/runtime sharding | `qa-testing-strategy` |
| **Security scanning** | CodeQL, Trivy, Semgrep, OpenSSF Scorecard in CI | `software-security-appsec`, `qa-security-testing` |
| **Dependency pinning** | Renovate config; SHA-pinned GitHub Actions | `software-security-appsec` |
| **ADR discipline** | Numbered ADRs with status transitions | `docs-codebase`, `software-architecture-design` |

## Patterns Worth Skipping

| Skip | Why |
|------|-----|
| Generic `npm install && npm test` workflows | Boilerplate, no signal |
| "Use feature branches" in CONTRIBUTING | Every repo says this; zero insight |
| PR templates asking only "what does this PR do?" | No discipline encoded |
| CODEOWNERS that assigns entire repo to one `@owner` | Not ownership, just formality |
| Release notes autogenerated with no human curation | Cadence-only signal, not content signal |

## Quality Filter (per candidate practice)

For each candidate practice, ask:

1. **Is it encoded in config/workflow, not just prose?** Prose rules drift. Enforced config is real.
2. **Is there evidence it's followed?** Check last 20 merged PRs — do they actually use the merge queue / required checks / CODEOWNERS routing? For a deeper check than eyeballing the PR list, run real git-history forensics: `blame -w -C -M --ignore-revs-file` to confirm CODEOWNERS reflects actual (non-mechanical) authorship, `range-diff` to confirm an advertised rebase/stacked-diff workflow stays clean across force-pushes, `bisect run` to confirm a "required check" actually catches the regression class it claims to. See [git-history-forensics.md](git-history-forensics.md).
3. **Is it specific to scale, or general?** "Merge queue" at a 50-person repo with parallel PRs means something; at a 2-person repo it's a formality.
4. **Is it the repo's invention, or inherited from a framework?** release-please in a Google repo is default; in a small team repo it's a deliberate choice.
5. **Does it survive the "obvious to a senior DevEx engineer" test?** If yes, skip. Signal lives in non-obvious setups.

## Extraction Output Format (per practice)

```markdown
### Practice: <short name>

**Source**: https://github.com/<owner>/<repo> at commit `<sha>`
**Extracted**: 2026-04-23
**License**: <SPDX-ID>
**Scorecard**: <n.n>
**Evidence**: <path(s) in the repo + last-20-PR usage signal>

**The practice**:
<1-3 sentence description in your own words — not copy-paste>

**Why it matters**:
<what process failure does this prevent, or what does it enable?>

**Preconditions** (when this practice makes sense):
- Repo size / team size
- CI minutes budget
- Tooling commitments

**Where it goes**:
- Target skill: `dev-git-workflow`
- Target file: `references/merge-queue-setup.md`
- Action: new section / new file / update existing

**Novel vs local**: new / extends existing / duplicates existing
**Confidence**: high / medium / low
```

## Common Mistakes in Practice-Scan Mining

- **Extracting practices that only work at that scale** — 1000-person-repo practices don't transfer to 5-person teams
- **Extracting the config without the rationale** — the *why* is what transfers, the YAML is just the encoding
- **Assuming popularity = best practice** — many popular repos have legacy config from 2019
- **Skipping the "is it followed?" check** — aspirational CONTRIBUTING.md is useless
- **Extracting security scanners without licensing context** — some (e.g. Snyk) require paid plans for closed-source teams
- **Ignoring required-check naming collisions** — check names are repo-local and won't transfer as-is
- **Trusting CODEOWNERS without a blame check** — a stale CODEOWNERS entry survives long after the named owner stopped touching the code; naive `git blame` (without `-w -C -M`) also over-credits reformat/rename commits — see [git-history-forensics.md](git-history-forensics.md)
